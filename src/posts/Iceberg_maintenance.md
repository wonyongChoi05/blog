Kafka 아키텍쳐는 최근 Zookeeper에서 정족수 기반 Kafka Raft(KRaft)라는 새로운 합의 프로토콜을 사용하는 컨트롤러로 진화했습니다.(Kafka 3.5부터는 KRaft만 지원) 이러한 아키텍쳐는 배포 간소화, 확장성 향상, 성능 향상 등의 장점을 가져왔습니다.

# Zookeeper

---

이전 카프카 클러스터에서 Zookeeper는 클러스터의 메타데이터 관리와 브로커 간 조율(coordination)을 담당하는 핵심 컴포넌트입니다.

Kafka에서 Zookeeper는 주로 다음과 같은 역할을 수행합니다.

1. 브로커 등록 및 감시

- kafka broker는 시작 시 zk에 자신을 등록합니다.
- 다른 브로커들도 이 정보를 통해 현재 클러스터에 어떤 브로커가 있는지 확인할 수 있습니다.
- zk는 ephemeral node(임시 노드)를 통해 브로커의 생존 여부를 감시합니다.

2. 컨트롤러 선출

- kafka 클러스터에는 하나의 브로커가 컨트롤러(controller) 역할을 맡아 파티션 리더 선출 등의 조율을 수행합니다.
- 컨트롤러 브로커는 zk를 통해 선출되며, 장애 시 자동으로 새로운 컨트롤러를 선출합니다.

3. 파티션 리더 선출 및 메타데이터 관리

- 각 토픽이 파티션은 여러 브로커에 복제되며, 이 중 하나는 리더 역할을 합니다.
- zk는 어떤 브로커가 어떤 파티션의 리더인지, 복제본은 어디에 있는지 등의 정보를 저장하고 제공합니다.

4. ACL 및 설정 정보 저장

- kafka 토픽 설정, acl, 사용자 인증 등 일부 메타데이터는 zk에 저장됩니다.

## zk 동작 과정

1. ZNode 구조

- Zookeeper는 파일 시스템처럼 /로 구분된 경로에 데이터를 저장합니다.
- 각 경로는 ZNode라고 하며, 일반 노드(persistent), 임시 노드(ephemeral), 시퀀스 노드(sequential) 등 다양한 타입이 있습니다.
- Kafka는 주로 ephemeral 노드를 사용해 브로커 생존 여부를 관리합니다.

2. Watch 메커니즘

- 클라이언트(Kafka 브로커)는 특정 znode에 watch를 걸어두고 변경사항을 감지합니다.
- 노드가 변경되거나 삭제되면 Zookeeper는 해당 이벤트를 watch한 클라이언트에게 알려줍니다.

3. Zookeeper Ensemble

- 고가용성을 위해 Zookeeper는 일반적으로 3대 이상의 서버로 구성된 Ensemble 형태로 운영됩니다.
- Zookeeper는 리더-팔로워 구조로 동작하며, ZooKeeper Atomic Broadcast(ZAB) 프로토콜을 통해 데이터 일관성을 보장합니다.
- 쓰기 작업은 리더가 처리하고, 다수결을 통해 커밋됩니다.

## 예시 시나리오

> Kafka 클러스터 구성: 브로커 3대, Zookeeper 3대

1. 모든 Zookeeper 서버가 올라감 → 리더 선출됨
2. 브로커 0, 1, 2가 Zookeeper에 /brokers/ids 아래에 자신을 등록
3. 브로커 1이 /controller에 노드 생성 → 컨트롤러 됨
4. 브로커 1이 토픽 logs의 파티션 0에 대해 브로커 2를 리더로 지정 → Zookeeper에 저장
5. 브로커 2 장애 발생 → ephemeral node 사라짐 → 컨트롤러가 감지하고 브로커 0을 새 리더로 지정

## 단점

- 확장성: zk는 많은 수의 클라이언트나 요청을 처리호도록 설계되지 않았습니다. kafka 클러스터의 크기와 트래픽이 증가함에 따라 zk가 병목 현상을 일으켜 kafka의 성능과 가용성에 영향을 미칠 수 있습니다.
- 복잡성: zk는 kafka 아키텍쳐에 복잡성과 종속성을 더합니다. kafka 사용자와 운영자는 zk를 kafka와 별도로 설치, 구성, 모니터링을 해야합니다. 또한 zk는 kafka와는 다른 자체 구성 파라미터, 장애 시나리오 및 보안 매커니즘을 가지고 있습니다.
- 일관성: zk는 강력한 일관성을 보장합니다. 즉, 클러스터의 모든 노드가 언제든지 동일한 데이터 뷰를 볼 수 있습니다. 하지만 이는 zk가 모든 요청을 처리하려면 과반수(쿼럼)의 노드가 필요하다는 것을 의미합니다.

# KRaft

KRaft는 Kafka Raft Metadata 모드를 의미하며, 이는 Kafka가 Zookeeper에 의존하는 대신 Raft 합의 프로토콜을 사용하여 자체 메타데이터를 관리한다는 것을 의미합니다.

## KRaft 동작 과정

1. 클러스터 시작 시

- Kafka를 KRaft 모드로 구성할 경우 process.roles=broker,controller 또는 둘 중 하나로 설정합니다.
- node.id로 각 노드를 식별합니다.
- 컨트롤러 후보 노드들이 Raft 기반으로 컨트롤러 선출을 시작합니다.
- 선출된 컨트롤러는 클러스터 메타데이터 관리를 시작합니다.

2. 메타데이터 로그 구성

- KRaft는 **메타데이터 로그(metadata topic)**를 내부 토픽 @metadata로 사용하여 아래 정보를 저장합니다:
- 브로커 등록
- 토픽 및 파티션 정보
- 파티션 리더
- ACL, 권한 정보
- 컨피그 설정 변경 등

3. 컨트롤러 동작

- KRaft 컨트롤러는 Zookeeper 컨트롤러와 동일한 역할을 수행하되, 모든 메타데이터를 Raft 기반 로그에 커밋합니다.
- 리더 선출, 브로커 장애 감지, ISR 변경 등의 정보는 모두 Raft consensus를 통해 복제되고 확정됩니다.

4. Raft 합의 알고리즘

- Raft는 leader-follower 구조로 동작하며, 컨트롤러 리더는 메타데이터 변경 사항을 follower 노드에 복제합니다.
- 다수의 follower가 확인한 후에만 커밋 → 일관성 보장.

## 예시 시나리오 (KRaft 클러스터)

> Kafka KRaft 클러스터: controller 3대, broker 5대

1. Kafka 노드 3대가 process.roles=controller로 실행됨 → Raft 통해 컨트롤러 리더 1대 선출
2. 브로커 5대가 컨트롤러와 통신 → @metadata 토픽에 브로커 등록 정보 커밋됨
3. 토픽 생성 요청이 들어오면 → 컨트롤러 리더가 메타데이터 로그에 토픽/파티션 정보 커밋
4. 브로커들은 메타데이터 로그를 pull하여 파티션 정보 동기화
5. 컨트롤러 리더 장애 발생 → 나머지 컨트롤러 후보들이 새로운 리더 선출

## 장점

- 단순성: KRaft는 별도의 조정 서비스가 필요 없도록 kafka 아키텍처를 단순화한다. kafka 사용자와 운영자는 두 개의 시스템이 아닌 하나의 시스템만 사용하면 된다. 또한 KRaft는 kafka 데이터 플레인과 동일한 구성, 파라미터, 장애 시나리오 및 보안 매커니즘을 사용하여 학습 곡선과 운영 오버헤드를 줄인다.
- 확장성: KRaft는 메타데이터 저장소의 부하를 줄여 카프카의 확장성을 향상시킨다. KRaft 모드에서는 컨트롤러 쿼럼만 Raft 프로토콜에 참여하고, 나머지 브로커는 컨트롤러 쿼럼과만 통신한다. 이를 통해 메타데이터 저장소를 거쳐야하는 연결 및 요청 수가 줄어들고, 카프카는 메타데이터 저장소의 성능과 가용성에 영향을 주지 않고 더 많은 브로커와 토픽을 처리할 수 있다.
- 가용성: KRaft는 메타데이터 저장소의 부분 장애를 허용하여 Kafka의 가용성을 향상시킵니다. KRaft 모드에서는 모든 요청을 처리하는 데 컨트롤러 쿼럼만 필요합니다. 일부 컨트롤러를 사용할 수 없어도 나머지 컨트롤러는 요청을 처리하고 클러스터 상태를 유지할 수 있습니다.
- 간소화된 배포 및 관리: Kafka 사용자는 더 이상 별도의 zk 클러스터를 실행하고 관리할 필요가 없습니다.
- 보안 강화: KRaft는 SSL/TLS 또는 SASL 매커니즘을 사용하여 클라이언트-서버 통신의 암호화 및 인증을 지원합니다.

# Trade-off

- 호환성 : KRaft는 이전 버전의 Kafka 또는 ZooKeeper와 호환되지 않습니다. ZooKeeper에서 KRaft로 마이그레이션하려는 사용자는 브로커와 클라이언트를 KRaft 모드를 지원하도록 업그레이드하고, 메타데이터를 ZooKeeper 형식에서 KRaft 형식으로 변환하고, 브로커를 ZooKeeper 모드에서 KRaft 모드로 전환하는 특정 절차를 따라야 합니다. 이는 신중한 계획과 테스트가 필요한 복잡하고 위험한 과정일 수 있습니다.
- 일관성 : KRaft는 경우에 따라 최종 일관성을 허용하여 ZooKeeper의 일관성 보장을 완화합니다. 예를 들어, 컨트롤러에 장애가 발생하거나 클러스터를 이탈하는 경우, 다른 컨트롤러가 해당 역할을 인계받고 클러스터 상태 뷰를 업데이트하는 데 시간이 걸릴 수 있습니다. 이 시간 동안 일부 브로커 또는 클라이언트는 캐시를 새로 고치거나 새 컨트롤러에 다시 연결할 때까지 오래되었거나 일관성이 없는 메타데이터를 볼 수 있습니다. 이로 인해 토픽 생성 또는 삭제, 파티션 재할당, 오프셋 커밋과 같은 일부 작업에서 일시적인 오류나 불일치가 발생할 수 있습니다.

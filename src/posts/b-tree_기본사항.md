# B-Tree Basic

---

이진 검색 트리(BST)는 효율적인 키-값 조회에 사용되는 정렬된 인메모리 데이터 구조다. BST는 여러 노드로 구성된다.

각 트리는 노드의 키와 이와 연관된 값, 두 개의 하위 포인터로 표현된다. BST는 루트 노드라고 하는 단일 노드에서 시작되며, 트리에는 루트가 하나만 있을 수 있다.

각 노드는 아래 그림처럼 검색 공간을 윈쪽과 오른쪽 하위 트리로 분할한다. 노드 키는 왼쪽 하위 트리에 저장된 키 보다 크고 오른쪽 하위 트리에 저장된 키보다 작다.

![이진트리노드불변성](/images/이진트리노드불변성.png)

트리의 루트에서 리프 레벨(노드에 자식이 없는 레벨)까지 왼쪽 포인터를 따라가면 트리 내에서 가장 작은 키를 가진 노드와 그 연관된 값을 찾을 수 있다.

마찬가지로 오른쪽 포인터를 따라가면 트리 내에서 가장 큰 키를 가진 노드와 그와 연관된 값을 찾을 수 있다. 값은 트리의 모든 노드에 저장할 수 있다. 검색은 루트 노드에서 시작되며, 검색된 키가 상위 레벨에서 발견되면 트리의 하위 레벨에 도달하기 전에 검색이 종료될 수 있다.

## 트리 밸런싱

삽입 연산은 특정 패턴을 따르지 않으며, 요소 삽입으로 인해 트리의 균형이 맞지 않는 상황이 발생할 수 있다. 최악의 시나리오는 좌우 밸런스를 갖춘 트리 대신 한쪽 방향으로 치우친 선형적인 병리학적 트리를 갖기되는 것이다.

![b](/images/균형잡힌트리와불균형또는병리적인트리예시.png)

트리의 균형을 맞추어야 하는 이유는 모든 요소가 트리의 한 쪽에 위치할 가능성은 낮지만, 적어도 일부 항목은 확실히 불균형 노드들로 위치하게 되어 검색 속도가 상당히 느려질 수 있기 때문이다.

균형 트리에서는 왼쪽 또는 오른쪽 노드 포인터를 따라가면 검색 공간이 평균적으로 절반으로 줄어들게 되므로 조회 복잡성은 대수적이다.

균형을 유지하는 방법 중 하나는 노드를 추가하거나 제거한 후 pivot 단계를 수행하는 것이다. 삽입 작업으로 인해 분기(branch)의 균형이 맞지 않는 경우 가운데 노드를 중심으로 노드를 회전시킬 수 있다.

![c](/images/회전단계예시.png)

## 디스크 기반 스토리지용 트리

불균형 트리의 경우 최악의 복잡도는 O(N)이다. 따라서 팬 아웃(노드당 허용되는 최대 자식 노드의 수)이 낮기 때문에 유지보수 비용이 증가하면 BST는 온디스크 데이터 구조로서 실용적이지 않다.

디스크에 BST를 유지하려면 몇 가지 문제에 직면하게 딘다. 한 가지 문제는 로컬리티다. 디스크는 데이터를 순차적으로 쓸 수 밖에 없는데, 이는 새로운 요소가 임의의 순서로 추가되기 때문에 부모 노드에 가깝게 쓰여진다는 보장이 없다. 따라서 노드 하위 포인터가 여러 디스크 페이지에 걸쳐 있을 수 있다는 뜻이다.

또 다른 문제는 트리의 높이이다. 트리 높이는 루트에서 가장 먼 노드(리프 노드)까지의 경로에 포함된 레벨의 수를 말한다.

이진 트리는 각 노드가 자식 노드를 최대 2개 가질 수 있다. 트리의 높이는 트리 안에 있는 노드 개수 N개와 관련 있다. 이상적인 경우 트리 높이는 log2(N)이다.

예를 들어
노드가 8개인 트리 -> 높이는 log2(8) = 3
노드가 16개인 트리 -> 높이는 log2(16) = 4
검색 비용은 트리의 높이에 비례한다. 검색할 때 트리 높이만큼 탐색을 수행해야 하므로 검색 시간은 O(log2(N))이다.

당연한 말이지만 B-Tree는 메모리에서의 탐색은 빠르지만, 디스크에서 데이터를 읽는 것은 느리다.

이진트리를 디스크에 구현하면, 노드를 탐색할 때마다 디스크에서 데이터를 읽어야 하고, 트리의 높이가 크면 탐색할 노드가 많아지고 디스크에서 데이터를 읽는 시간이 길어진다. 결과적으로 디스크 접근 횟수 == 트리 높이가 된다.

따라서 Fan-Out이 중요한데, 이진 트리는 팬아웃이 2, 2-3 트리는 팬아웃이 23, B-Tree는 100개 이상으로 많다. 팬아웃이 커질수록 한 노드에서 더 많은 자식 노드를 가질 수 있다. 그러면 트리 높이가 줄어들고 탐색 시간이 줄어든다.

- 팬아웃 2 (이진트리): 노드 16개 -> 높이 4
- 팬아웃 4 (4-트리): 노드 16개 -> 높이 2

### 디스크에 적합한 트리란?

디스크는 데이터를 블록 단위로 읽는다. 즉, 한 번 읽을 때 여러 데이터를 가져올 수 있다. 팬아웃이 큰 트리(B-Tree)는 한 노드에 더 많은 데이터를 저장하기 때문에 한 번 디스크를 읽을 때 더 많은 데이터를 가져오므로 탐색 속도가 빨라진다. 결과적으로 디스크에서의 효율적인 탐색이 가능하다.

이러한 요소를 고려할 때 디스크 구현에서 BST보다 더 적합한 트리는 다음과 같은 특징을 보여야한다.

- 높은 팬아웃으로 인접 키의 로컬리티를 개선한다.
- 탐색 횟수를 줄이기 위해 높이를 낮춘다.

# 디스크 기반 구조

온디스크 데이터 구조는 데이터의 양이 너무 커서 전체 데이터 세트를 메모리에 보관하는 것이 불가능하거나 타당하지 않을 때 자주 사용된다. 데이터의 일부만 메모리에 캐시하고 나머지는 효율적으로 액세스할 수 있는 방식으로 디스크에 저장해야 한다.

## HDD

HDD는 움직이는 기계 부품을 사용한다. 내부에 자기 디스크(플래터)가 있고, 데이터를 디스크 표면에 저장한다. 데이터를 읽고 쓰기 위해 헤드가 디스크 위를 이동한다.

HDD 작동 과정은 다음과 같다.

1. 디스크가 고속으로 회전한다.
2. 헤드가 회전하는 디스크 위의 특정 위치로 이동해 데이터를 읽거나 쓴다.
3. 이 과정은 물리적인 움직임이 필요하므로 시간이 걸린다.

이처럼 HDD는 물리적인 부품을 이동시키는 시간이 필요해 속도가 느리다.

## SSD

SSD는 움직이는 부품이 없으며, 데이터를 저장하는데 플래시 메모리 칩을 사용한다. 전기 신호만으로 데이터를 읽고 쓰기 때문에 HDD에 비해 매우 빠르다.

SSD 작동 과정은 다음과 같다.

1. 데이터를 저장하거나 읽을 때 반도체 칩이 전기 신호를 사용한다.
2. 물리적인 움직임 없이 바로 접근할 수 있어 속도가 빠르다.

이처럼 SSD는 데이터를 전기적으로 읽고 쓰므로 매우 빠르다.

SSD(Solid State Drive)는 회전하는 디스크나 읽기를 위해 위치해야 하는 헤드가 없다. 일반적인 SSD는 메모리 셀로 구성되며, 문자열로 연결되고, 문자열은 array로 결합되고, array는 page로 결합되고, page는 block으로 결합된다.

![d](/images/SSD_구성도.png)

쓰기 또는 읽을 수 있는 가장 작은 단위는 Page이다. 그러나 빈 메모리 셀에 대해서만 변경할 수 있다. 가장 작은 지우기 엔티티는 페이지가 아니라 여러 페이지를 담고 있는 블록이기 때문에 종종 지우기 블록이라고 한다.

# 유비쿼터스 B-Trees

B-Tree는 정렬되어있다. B-Tree 노드 내부의 키는 순서대로 저장된다. 따라서 검색된 키를 찾기 위해 이진 검색과 같은 알고리즘을 사용할 수 있다. 예를 들어 40억 개(10^9) 항목 중에서 검색된 키를 찾으려면 약 32개의 비교가 필요하다. 이러한 비교를 각각 수행할 때 디스크 탐색을 수행해야 한다면 속도가 상당히 느려지지만, B-Tree 노드는 수십, 수백 개의 항목을 저장하므로 레벨 점프 한 번만 디스크 탐색을 수행하면 된다.

B-Tree를 사용하면 Point Query와 Range Query를 모두 효율적으로 실행할 수 있다. 대부분의 쿼리 언어에서 같음(=)으로 표현되는 포인트 쿼리는 단일 항목을 찾는다. 반면에 비교(<=>)로 표현되는 레인지 쿼리는 여러 데이터 항목을 순서대로 쿼리하는 데 사용된다.

## B-Tree 계층 구조

B-Tree는 여러 노드로 구성된다. 각 노드는 최대 N개의 키와 자식 노드에 대한 N + 1개의 포인터를 보유한다. 이러한 노드는 논리적으로 3개의 그룹으로 그룹화 된다. (Root, Internal, Leaf)

B-Tree는 페이지 구성 기법이기 때문에 노드와 페이지라는 용어를 같은 의미로 사용하는 경우가 많다. B-Tree는 각 노드에 저장된 키의 수인 팬아웃으로 특정지어진다.

팬 아웃이 클수록 트리의 균형을 유지하는데 필요한 구조 변경 비용을 절감하고, 단일 블록 또는 여러 개의 연속된 블록에 하위 노드에 대한 키와 포인터를 저장하여 탐색 횟수를 줄이는 데 도움이 된다. 밸런싱 작업은 노드가 가득 차거나 거의 비어있을 때 트리가 트리거 된다.

> 앞서 언급한 B-Tree의 데이터 구조의 정확한 이름은 B+ -Tree이다. 또는 팬아웃이 높은 트리를 멀티웨이트리라고 부른다.

> B-Tree를 사용하면 루트, 내부, 리프 노드 등 모든 레벨에 값을 저장할 수 있다. B+ -Tree는 리프 노드에만 값을 저장한다. 내부 노드에는 리프 레벨에 저장된 연관된 값으로 검색 알고리즘을 안내하는 데 사용되는 구분 기호 키만 저장한다.

### 구분 기호 키

B-Tree 노드에 저장된 키를 인덱스 항목, 구분 키 또는 디바이더 셀이라고 한다. 이들은 트리를 서브트리로 분할하여 서로 연관된 키 범위를 가진다. 키는 이진 검색이 가능하도록 정렬된 순서로 저장된다. 하위 트리는 키를 찾아 상위 레벨에서 하위 레벨로 해당 포인터를 따라가면 찾을 수 있다.

노드의 첫 번째 포인터는 첫 번째 키보다 작은 항목을 보유한 하위 트리를 가리키고, 노드의 마지막 포인터는 마지막 키보다 크거나 같은 항목을 보유한 하위 트리를 가리킨다.

## B-Tree 조회 알고리즘

B-Tree에서 항목을 찾으려면 루트에서 리프까지 한 번의 탐색을 수행해야 한다. 이 검색의 목적은 검색된 키 또는 그 이전 키를 찾는 것이다.

정확히 일치하는 항목을 찾는 것은 포인트 쿼리, 업데이트 및 삭제에 사용되며, 이전 항목을 찾는 것은 범위 스캔 및 삽입에 유용하다.

알고리즘은 루트 노드부터 시작하여 검색하려는 키를 루트 노드의 키들과 이진 검색으로 비교하고 검색된 키보다 큰 첫 번째 구분 키를 찾아 해당 키와 연결된 하위 트리 포인터를 따라간다.

같은 과정을 반복하며 더 구체적인 범위를 나타내는 하위 트리로 이동한다. 리프 노드에서 검색된 키를 찾거나 키가 없으면 이전 키를 찾는다.

만약 포인트 쿼리에서 키를 찾으면 반환하고, 없으면 "존재하지 않음"을 반환한다. 레인지 쿼리에서는 범위에 해당하는 키-값 쌍을 찾고, 형제 노드의 포인터를 따라가며 검색을 이어간다.

조회는 루트에서 리프까지 한 번의 탐색으로 이루어지며, 각 레벨에서는 키가 더 세밀하게 구분되어, 마지막에는 리프 노드에서 데이터를 찾는다. 범위 검색에서는 형제 포인터를 통해 빠르게 키들을 순차적으로 탐색한다.

## B-Tree 노드 분할

값을 B-Tree에 삽입하려면 먼저 대상 리프의 위치를 찾아야 한다. 이를 위해 이전 섹션에서 설명한 알고리즘을 사용한다. 리프를 찾은 후에는 키와 값을 추가한다. B-Tree의 업데이트는 조회 알고리즘을 사용하여 대상 리프 노드를 찾고 새 값을 기존 키에 연결하는 방식으로 동작한다.

대상 노드에 사용 가능한 공간이 충분하지 않은 경우, 오버플로우가 발생하여 기존 노드가 분할된다.

```css
       [20]
      /    \
 [10, 15] [25, 30]
```

예를 들어 새로운 값 12를 삽입할 때

1. 리프 노드 [10, 15]에서 적절한 위치를 찾는다. -> [10, 12, 15]
2. 리프 노드에 공간이 충분하므로 그냥 추가한다. -> 완료

새로운 값 18을 삽입할 때

1. 리프 노드 [10, 15]에 적절한 위치를 찾는다. -> [10, 15, 18]
2. 노드가 가득 차므로 중간 값을 부모 노드로 올린다. -> 15가 부모 노드로 승격하며, 부모 노드가 1개 늘어나고, 18번 노드가 생성된다.

```css
         [15 | 20]
        /    |     \
   [10]    [18]  [25, 30]
```

이렇게 분할은 새 노드를 할당하고 분할 노드의 요소 중간 값을 부모 노드로 전송한 다음 키와 포인터를 부모 노드에 추가하는 방식으로 이루어 진다. 이 과정이 루트까지 전파되면 트리 높이가 증가하게 된다.

## 요약

이진 검색 트리는 B-Tree와 비슷한 복잡성을 가지지만, 팬아웃이 낮고 밸런싱으로 인한 재배치 및 포인터 업데이트가 많기 때문에 디스크에 적합하지 않다. B-Tree는 각 노드에 저장되는 항목 수를 늘리고(높은 팬아웃) 밸런싱 작업 빈도를 줄임으로써 이 두 가지 문제를 모두 해결한다.

# 파일 형식

---

B-Tree의 기본적인 의미를 살펴보았으니 이제 디스크에서 B-Tree와 다른 구조가 정확히 어떻게 구현되는지 살펴보자.

데이터 레이아웃은 디스크가 메모리보다 훨씬 더 중요하다. 디스크에서의 데이터 구조가 효율적이려면, 디스크에 빠르게 액세스할 수 있는 방식으로 데이터를 배치하고, 영구 저장 매체의 특성을 고려하고, 이진 데이터 형식을 생각해 내고, 데이터를 효율적으로 직렬화 및 역직렬화할 수 있는 방법을 찾아야 한다.

운영체제와 파일 시스템이 일부 책임을 대신하지만, 온디스크 구조를 구현하려면 더 많은 세부 사항에 주의를 기울여야 한다.

## 바이너리 인코딩

디스크에 데이터를 효율적으로 저장하려면 압축적이고 직렬화 및 역직렬화하기 쉬운 포맷을 사용하여 인코딩 해야한다. 바이너리 포맷에 대해 이야기할 때 레이아웃이라는 단어를 자주 듣게 된다.

malloc, free와 같은 프리미티브가 없고 읽기, 쓰기만 있기 때문에 액세스를 다르게 생각하고 그에 따라 데이터를 준비해야 한다.

## 프리미티브 유형

키와 값은 정수, 날짜 또는 문자열과 같은 유형을 가지며 원시 바이너리 형식으로 다시 전송할 수 있다. 대부분의 숫자 데이터 유형은 고정 크기 값으로 표현된다. 멀티바이트 숫자 값으로 작업할 때는 인코딩과 디코딩 모두에 동일한 바이트를 사용하는 것이 중요하다.

컴퓨터가 데이터를 저장하거나 전송할 때 숫자와 같은 값을 직렬화하거나 역직렬화한다. 이때 숫자의 바이트 순서를 어떻게 저장할지 정하는 규칙을 엔디안성이라고 한다.

### 빅 엔디안

- 중요한 바이트(MSB)가 먼저 저장된다.
- 예를 들어, Hello라는 단어는 H(0x48) e(0x65) l(0x6C) l(0x6C) o(0x6F)로 이루어 지는데 이 때 빅 엔디안에서는 가장 왼쪽의 0x48가 먼저 저장된다.
- 순서: 0x48 0x65 0x6C 0x6C 0x6F

### 리틀 엔디안

- 덜 중요한 바이트(LSB)가 먼저 저장된다.
- 예를 들어, Hello라는 단어는 H(0x48) e(0x65) l(0x6C) l(0x6C) o(0x6F)로 이루어 지는데 이 때 리틀 엔디안에서는 가장 오른쪽의 0x6F 먼저 저장된다.
- 순서: 0x6F 0x6C 0x6C 0x65 0x48

예를 들어 쓰기는 리틀 엔디안으로 쓰고, 읽을 때는 빅 엔디안으로 읽을 때 RocksDB는 호환성을 위해 EndianTransform을 통해 바이트 순서를 반대로 바꾸는 작업을 수행한다.

레코드는 숫자, 문자열, Bool 및 이들의 조합과 같은 기본 요소로 구성된다. 하지만 네트워크를 통해 데이터를 전송하거나 디스크에 저장할 때는 바이트 시퀀스만 사용할 수 있다. 즉, 레코드를 전송하거나 쓰기 위해서는 직렬화(해석 가능한 바이트 시퀀스로 변환, Hello -> H(0x48) e(0x65) l(0x6C) l(0x6C) o(0x6F))해야 하고, 수신 또는 읽기 후에 사용하려면 역직렬화(바이트 시퀀스를 원래 레코드로 변환, H(0x48) e(0x65) l(0x6C) l(0x6C) o(0x6F) -> Hello)해야 한다.

바이너리 데이터 형식에서는 항상 더 복잡한 구조의 빌딩 블록 역할을 하는 기본 요소부터 시작한다. 바이트 값은 8비트, 숏은 2바이트(16비트), 인트는 4바이트(32비트), 8바이트(64비트) 등 숫자 유형이 따라 크기가 다를 수 있다.

## 문자열 및 가변 크기 데이터

모든 기본 숫자 유형은 크기가 고정되어 있다. 기본값을 구조체로 결합하고 고정 크기 배열이나 다른 메모리 영역에 대한 포인터를 사용할 수 있는 것은 C의 구조체와 비슷하다.
